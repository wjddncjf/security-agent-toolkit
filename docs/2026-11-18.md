## 1. ping

### 문제 결과 화면 읽기

- **보냄 · 받음 · 손실 · 평균:** 4개 · 4개 · 0개(0%) · 46.014ms
- **손실 %는 보낸 수와 받은 수로 어떻게 계산했나요?**
  - 답: `(보낸 패킷 수 - 받은 패킷 수) ÷ 보낸 패킷 수 × 100`으로 계산한다. 이번 실습에서는 4개를 보내고 4개를 모두 받았으므로 손실률은 0%이다.

※ 과제 예시 화면 대신 직접 측정한 값을 기록했다.

### 문제 구글 DNS 서버에 `ping` 열 번 보내기

- **`8.8.8.8`까지 평균 왕복 시간 · TTL · 받음 · 손실:** 48.747ms · 114 · 10개 · 0개(0%)

### 문제 이름으로 `ping` 보내기

- **`google.com`의 IP 주소:** 142.250.198.206
- **이름만 입력했는데 IP 주소가 나온 이유는 무엇인가요?**
  - 답: DNS가 `google.com`이라는 도메인 이름을 IP 주소로 변환하기 때문이다. 컴퓨터는 DNS를 통해 확인한 IP 주소를 이용하여 해당 서버와 통신한다.

### 문제 두 가지 실패를 구별하기

- **두 실패 문구:** `Unknown host`, `Request timeout`
- **두 실패는 각각 어디에서 멈춘 것인가요?**
  - 답: `Unknown host`는 DNS가 도메인 이름을 IP 주소로 변환하지 못한 경우이다. 반면 `Request timeout`은 IP 주소로 ping을 시도했지만 정해진 시간 안에 응답을 받지 못한 경우이다. 실제로 `192.0.2.1`에 ping을 보냈을 때 패킷 4개가 모두 손실되었다.

### 찾아본 것

- **2.1 표에서 찾아 쓴 TTL의 뜻과 라우터를 지날 때 바뀌는 방식:** TTL(Time To Live)은 패킷이 네트워크에서 무한히 전달되지 않도록 제한하는 값이다. 라우터를 통과할 때마다 1씩 감소하며, 더 이상 전달할 수 없을 정도로 줄어들면 패킷을 폐기한다. 이번 실습에서는 수신한 응답 패킷의 TTL이 114로 표시되었다.

### 이 교시에 새로 안 것

- **이 교시에서 새로 알게 된 것:** ping을 통해 패킷 손실률과 왕복 시간을 확인하는 방법을 알게 되었다. 또한 IP 주소로 직접 통신하는 경우와 DNS를 통해 도메인 이름을 변환하는 경우의 차이를 이해했다. 통신 실패도 이름 해석 실패와 응답 시간 초과로 구분할 수 있다는 점을 알게 되었다.

## 2. IP와 MAC

### 문제 결과 화면 읽기

- **직접 확인한 IPv4 주소 · MAC 주소 · 기본 게이트웨이:** 192.168.200.29 · 3a:58:df:26:6f:1e · 192.168.200.1

※ 과제의 예시 화면을 확인하지 못해 실제 MacBook에서 측정한 값으로 기록했다.

### 문제 내 IP 주소 · 게이트웨이 · MAC 주소 찾기

- **찾은 장치 이름 · 내 IPv4 주소 · 기본 게이트웨이 · MAC 주소(물리적 주소):** en0 · 192.168.200.29 · 192.168.200.1 · 3a:58:df:26:6f:1e

### 문제 게이트웨이까지 `ping`

- **게이트웨이까지 평균 · 2-2의 `8.8.8.8` 평균:** 7.141ms · 48.747ms
- **게이트웨이까지가 더 짧은 이유는 무엇인가요?**
  - 답: 기본 게이트웨이는 같은 로컬 네트워크에 있어 가까운 경로로 통신할 수 있다. 반면 Google DNS 서버는 외부 네트워크에 있으므로 여러 네트워크 장비를 거쳐야 한다. 따라서 이번 실습에서는 게이트웨이까지의 왕복 시간이 더 짧게 측정되었다.

### 문제 ARP 캐시 보기 — `arp -a`

- **게이트웨이 줄의 MAC 주소 · 유형:** 70:5d:cc:e9:ca:34 · Ethernet(동적 ARP 항목으로 판단)
- **🔍 ARP는 무엇을 알아내려고 쓰나요? 내 결과의 게이트웨이 줄을 예로 들어 설명합니다.**
  - 답: ARP는 같은 로컬 네트워크에서 IPv4 주소에 대응하는 MAC 주소를 알아내기 위해 사용한다. 이번 실습에서는 게이트웨이 `192.168.200.1`에 대응하는 MAC 주소가 `70:5d:cc:e9:ca:34`임을 확인했다. 이를 통해 게이트웨이로 이더넷 프레임을 전송할 때 사용할 목적지 MAC 주소를 알 수 있다.

### 이 교시에 새로 안 것

- **이 교시에서 새로 알게 된 것:** IP 주소는 네트워크에서 장치를 구분하는 논리적 주소이고, MAC 주소는 네트워크 인터페이스를 식별하는 주소라는 차이를 알게 되었다. 또한 `arp -a` 명령어로 IP 주소와 MAC 주소의 대응 관계를 확인할 수 있다는 것을 배웠다.

## 3. 포트

### 문제 직접 실행해 보기

- **출력 두 줄:** `HTTPS`, `모름`
- **`3389`는 사전에 없는데도 에러 없이 둘째 줄이 나온 이유는 무엇인가요?**
  - 답: 딕셔너리의 `get()` 메서드는 해당 키가 없으면 지정한 기본값을 반환하기 때문이다. 따라서 3389가 딕셔너리에 없어도 오류 대신 `"모름"`이 출력된다.

### 문제 지금의 연결과 그 프로그램 — `netstat -ano`

- **고른 줄의 외부 포트 → 서비스 이름 · PID → 프로그램 이름:** 443 → HTTPS · 91151 → codex

※ macOS 환경이므로 Windows의 `netstat -ano` 대신 `lsof -nP -iTCP -sTCP:ESTABLISHED`를 실행하여 확인했다.

### 문제 내 PC의 LISTENING 포트 찾기

- **4.1 표에 있는 LISTENING 포트 → 서비스 이름:** 해당 없음. 현재 확인된 TCP LISTENING 포트 중 4.1 표에 나열된 포트는 없었다.

- **🔍 LISTENING과 ESTABLISHED는 무엇이 다른가요? 4-2와 4-3에서 본 줄을 예로 들어 설명합니다.**
  - 답: LISTENING은 프로그램이 연결 요청을 기다리는 상태이고, ESTABLISHED는 상대와 TCP 연결이 성립된 상태이다. 이번 실습에서 `aside-dae`의 21420 포트는 LISTENING 상태였으며, `codex`가 외부 443 포트에 연결된 통신은 ESTABLISHED 상태였다.

### 문제 증상으로 층 좁히기

- **증상 ① · ② · ③에서 의심되는 층:**
  - ① 응용 계층(7계층) — DNS
  - ② 데이터 링크 계층(2계층) 또는 네트워크 계층(3계층)
  - ③ 응용 계층(7계층) 또는 전송 계층(4계층)

- **증상마다 그렇게 판단한 근거는 무엇인가요?**
  - 답:
    - ① IP 주소로 ping이 성공하지만 도메인 이름으로 실패하므로 DNS 이름 해석 문제를 의심할 수 있다.
    - ② 기본 게이트웨이에도 ping이 실패하므로 로컬 네트워크 연결이나 IP 설정, 라우팅 문제를 의심할 수 있다.
    - ③ ping은 정상적으로 작동하므로 기본적인 IP 통신은 가능하지만, 특정 웹사이트만 접속되지 않는다면 웹 서버나 HTTPS, TCP 연결 관련 문제를 의심할 수 있다.

### 찾아본 것

- **4.1 표에서 찾아 쓴 3389의 위험과 445를 이용해 퍼진 랜섬웨어:** 3389는 Windows 원격 데스크톱(RDP)에 사용하는 포트이다. 인터넷에 노출되면 비밀번호 무차별 대입 공격이나 취약점 악용을 통한 무단 접근 위험이 있다. 445는 Windows 파일 공유에 사용하는 SMB 포트이며, 워너크라이(WannaCry) 랜섬웨어가 SMBv1 취약점을 악용해 네트워크 내 다른 컴퓨터로 확산된 사례가 있다.

### 이 교시에 새로 안 것

- **이 교시에서 새로 알게 된 것:** 포트 번호를 통해 통신에 사용되는 서비스의 종류를 구분할 수 있다는 것을 알게 되었다. 또한 macOS에서는 `lsof` 명령어로 프로그램의 PID와 TCP 연결 상태를 확인할 수 있었다. LISTENING은 연결 요청을 기다리는 상태이고, ESTABLISHED는 연결이 성립된 상태라는 차이를 이해했다.
